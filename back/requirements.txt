# OpenTelemetry for the stdio UPSTREAMS this container spawns, not for the
# gateway itself (yet — that's its own Kanban card). Same reason `mcp` and
# `flights` below are here: a Tier-1 app's aw-app.json runtime.pip_requires
# installs nothing into this (separate) container, and `python3 -m
# <app>.mcp_server` runs against THIS image's interpreter.
#
# Today's consumer is aw-app-agents-platform-runners' MCP child
# (agents_platform_runners_app/mcp_otel.py), which every agent's run-dispatch
# path goes through: without the SDK here it emitted no spans, propagated no
# traceparent to agents-platform-multitenant, and reached SigNoz only as
# untagged container-stdout text (Kanban observability:runners-app-no-otel-
# instrumentation). Its import is guarded, so this pin and that app's release
# can land in either order.
#
# Pinned to aw-workspace core's own versions (its requirements.txt lines
# 33-36) so one workspace doesn't run two OTel SDK generations. Note the
# deliberate omission of opentelemetry-instrumentation-requests: the OTLP
# http exporter is built on `requests`, so instrumenting it makes the
# exporter trace its own POST — a feedback loop. Core skips it for the same
# reason.
opentelemetry-sdk==1.40.0
opentelemetry-exporter-otlp-proto-http==1.40.0
opentelemetry-instrumentation-httpx==0.61b0
# For local stdio upstreams that are themselves built on the official MCP
# Python SDK (today: aw-app-devctl's devctl-browser, `from mcp.server.fastmcp
# import FastMCP`) — those apps declare this in their own aw-app.json
# runtime.pip_requires, but that field isn't actually enforced by the
# platform (installs nothing), and a Tier-1 app has no way to install
# anything into this (separate, Tier-2) container anyway. Bundled here for
# the same reason nodejs/npm already are (Dockerfile) — upstreams spawned
# via bare "python3"/"npx" need their runtime available in THIS image.
# Pinned below 2.0: that release moved/renamed FastMCP (mcp==2.0.0 has no
# mcp.server.fastmcp submodule at all) — devctl-browser's code targets the
# 1.x API shape, matching its own aw-app.json's declared "mcp>=1.2".
mcp>=1.2,<2.0
# Same reasoning, same fix, for aw-app-travel's stdio upstream (`python3 -m
# travel_app.mcp_server`): its aw-app.json declares runtime.pip_requires,
# which — like every Tier-1 app's pip_requires — installs nothing into this
# Tier-2 container. Without it the child crashes on `from fli.core import
# ...` before ever answering the handshake; the gateway sees the pipe die
# mid-negotiation and logs a misleading "WriteUnixTransport closed"
# RuntimeError instead of the real ModuleNotFoundError (stderr is DEVNULL'd
# in Upstream._spawn()). Pinned to the same merged-but-unreleased upstream
# commit aw-app-travel's own pip_requires uses (PyPI's flights==0.9.0 has
# Google's August x-goog-batchexecute-bgr RPC change unfixed, see
# github.com/punitarani/fli issue #223 / PR #230) — keep these two in sync.
# Archive tarball, not git+https: this image's base has no `git` binary and
# pip's VCS installer hard-requires one even for a single commit checkout.
